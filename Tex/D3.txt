\section{Architecture Overview}
\subsection{System Structure}
Bhasha Quest uses layered MVC with strict separation of UI, controller, domain, and data. The final design adds dual streams (Nepali, Kannada) and unit-based progression (3 exercises per unit) surfaced in a Path tab. A dedicated Path view surfaces status and locking; the controller orchestrates grading, progression, and persistence via repositories.

\subsection{Key Architectural Principles}
\begin{itemize}
  \item \textbf{Strict Layering:} UI $\rightarrow$ Controller $\rightarrow$ Domain $\rightarrow$ Data; domain has no UI knowledge.
  \item \textbf{Streams \& Units:} Content organized into streams with units of 3 exercises; Path tab shows completed/current/locked units with admin override.
  \item \textbf{Controller as Orchestrator:} \texttt{AppController} holds stream/unit context, picks graders at runtime, updates profile/XP/streak, persists via repositories, emits unit completion.
  \item \textbf{Signals/Slots for Decoupling:} UI emits actions; controller emits state/results/errors; keeps dependencies one-way.
  \item \textbf{Repository Abstraction:} JSON repositories for content and profile; SQLite profile repo behind the same interface for future backend swap.
  \item \textbf{Error Handling:} Controller surfaces repo/audio issues via signals; Path respects locks unless admin override (admin123).
\end{itemize}

\subsection{Requirements Coverage}
\begin{itemize}
  \item \textbf{Dual Languages:} Two parallel learning streams (Nepali, Kannada) with independent units and content.
  \item \textbf{Structured Units:} Each unit holds exactly 3 exercises; Path tab visualizes progress and locking.
  \item \textbf{Exercise Variety:} MCQ, Translate (text/character selection), TileOrder, Listen (audio MCQ), Speak (stub evaluator); audio integrated.
  \item \textbf{Progress Tracking:} XP, streak, skill mastery, per-stream unit completion persisted; UI shows date and streak controls.
  \item \textbf{Patterns Implemented:} Factory + Singleton (creational), Strategy + Observer (behavioral), all in active use.
  \item \textbf{Testing:} GoogleTest/GoogleMock harness; core logic tests included and passing.
\end{itemize}

\subsection{Notable Implementation Details}
\begin{itemize}
  \item \textbf{Path Locking \& Admin Override:} Units unlock sequentially; admin password can bypass locks for demos/testing.
  \item \textbf{Unit Completion Dialog:} Confetti animation + “Keep Learning” action wired to controller continuation.
  \item \textbf{Character Picker:} Per-language character sets flow from content JSON to the widget, which rebuilds its grid dynamically.
  \item \textbf{Audio Resolution:} AudioManager resolves relative paths under \texttt{assets/}; missing files are safely ignored.
  \item \textbf{Persistence Shape:} Profile JSON stores completed units; SQLite schema includes unit progress table for future DB promotion.
\end{itemize}

\section{Modules and Responsibilities}
\subsection{UI Layer}
\begin{itemize}
  \item \textbf{HomeView:} Stream cards, profile shortcut.
  \item \textbf{LessonView:} Prompts, MCQ list (click-to-fill), character picker, audio play, unit progress label, feedback.
  \item \textbf{PathView:} Unit list per stream with status; prompts for admin password on locked units.
  \item \textbf{ProfileView:} Learner Hardik, XP, streak, skills; +1 day button for streak testing.
  \item \textbf{UnitCompleteDialog:} Lightweight animation and continue action.
\end{itemize}
\subsection{Controller Layer}
\begin{itemize}
  \item \textbf{AppController:} Loads streams/units, tracks indices, selects graders (Strategy), updates profile (Observer), persists via repository, emits unitCompleted/streamFinished/unitProgress/errors.
\end{itemize}
\subsection{Domain Layer}
\begin{itemize}
  \item \textbf{Exercises:} MCQ, Translate (character selection), TileOrder, Listen, Speak stub.
  \item \textbf{Graders (Strategy):} MCQ/Translate/CharacterSelection/TileOrder/Listen/Speak.
  \item \textbf{Progress:} Profile (Subject/Observer), SkillProgress, SRSScheduler.
  \item \textbf{Creational:} ExerciseFactory (Factory), AudioManager (Singleton).
  \item \textbf{Structure:} LearningStream, Unit (vector of unique\_ptr<Exercise>).
\end{itemize}
\subsection{Data Layer}
\begin{itemize}
  \item \textbf{Repositories:} JsonContentRepository, JsonProfileRepository, SQLiteProfileRepository (schema-ready).
  \item \textbf{Assets:} Audio files under \texttt{code/assets/audio}; content under \texttt{code/core/data/content.json}.
\end{itemize}

\section{Flows and Behavior}
\subsection{Unit Progression Flow}
\begin{enumerate}[label=\textbf{\arabic*.}]
  \item User selects stream/unit (Home/Path); controller loads streams and sets indices.
  \item LessonView shows exercise; user submits; controller grades (Strategy), updates profile (Observer), plays audio (Singleton).
  \item After last exercise: controller marks unit complete, persists profile, emits \texttt{unitCompleted}; UI shows dialog and continues on user action.
  \item Path reflects completion; next unit unlocks; admin override can bypass lock.
\end{enumerate}
\subsection{UI Styling and Interactions}
\begin{itemize}
  \item LessonView: progress label, click-to-select MCQ, character picker for selection mode, audio button visible when audioPath exists.
  \item PathView: dual columns (Nepali/Kannada), locked items greyed; admin prompt on locked double-click.
  \item ProfileView: hardcoded learner “Hardik”; streak/date control for testing.
  \item Dialog: confetti animation and CTA to continue.
\end{itemize}
\subsection{Error Handling and Robustness}
\begin{itemize}
  \item Missing content/profile file: controller emits error; UI message box.
  \item Missing audio file: AudioManager quietly ignores; no crash.
  \item Bounds checks: controller guards stream/unit/exercise indices and emits errors on invalid state.
  \item Path locking: enforced by completion; admin override requires password.
  \item Future: stronger JSON validation, retries, and logging.
\end{itemize}

\section{Design Patterns}
\subsection{Factory: \texttt{ExerciseFactory} (Creational)}
\textbf{Location:} \texttt{code/core/domain/ExerciseFactory.h/cpp}.\\
\textbf{Why:} Centralizes creation of MCQ, Translate, TileOrder, Listen, Speak from JSON; avoids conditional sprawl; preserves Open/Closed.\\
\textbf{How:} \texttt{createExercise(type,spec)} dispatches to type-specific builders; supports audio paths, character sets, selection flags.\\
\textbf{Benefit:} Localized construction, easy extension, tested in isolation.

\noindent\textbf{Snippet:}
\begin{lstlisting}[caption={Factory dispatch}, captionpos=b]
Exercise* ExerciseFactory::createExercise(const QString& type,
                                          const QJsonObject& spec) {
    if (type == "MCQ") return createMCQ(spec);
    if (type == "Translate") return createTranslate(spec);
    if (type == "TileOrder") return createTileOrder(spec);
    if (type == "Listen") return createListen(spec);
    if (type == "Speak") return createSpeak(spec);
    return nullptr;
}
\end{lstlisting}

\subsection{Singleton: \texttt{AudioManager} (Creational)}
\textbf{Location:} \texttt{code/core/domain/AudioManager.h/cpp}.\\
\textbf{Why:} Single \texttt{QMediaPlayer}/\texttt{QAudioOutput} to avoid resource contention and duplicate init.\\
\textbf{How:} Meyers singleton; \texttt{playAudio()}, \texttt{playSuccess()}, \texttt{playError()}; deleted copy/move.\\
\textbf{Benefit:} Controlled audio lifecycle; callable from controller/UI without extra players.
\newpage
\subsection{Strategy: \texttt{StrategyGrader} Hierarchy (Behavioral)}
\textbf{Location:} \texttt{code/core/domain/StrategyGrader.h} and concrete graders.\\
\textbf{Why:} Different grading algorithms per exercise type; keeps Exercise/AppController slim.\\
\textbf{How:} Abstract \texttt{grade()}; concrete MCQ/Translate/TileOrder/Listen/Speak/CharacterSelection; runtime selection in \texttt{AppController}.\\
\textbf{Benefit:} Swap/extend grading without touching controllers; unit-tested.

\noindent\textbf{Snippet:}
\begin{lstlisting}[caption={Runtime strategy selection}, captionpos=b]
std::unique_ptr<StrategyGrader> AppController::createGraderFor(
    const Exercise* ex) const {
    if (ex->type() == "MCQ") return std::make_unique<MCQGrader>();
    if (ex->type() == "Translate") {
        auto tr = dynamic_cast<const TranslateExercise*>(ex);
        if (tr && tr->usesCharacterSelection())
            return std::make_unique<CharacterSelectionGrader>();
        return std::make_unique<TranslateGrader>();
    }
    if (ex->type() == "TileOrder") return std::make_unique<TileOrderGrader>();
    if (ex->type() == "Listen") return std::make_unique<ListenGrader>();
    if (ex->type() == "Speak") return std::make_unique<SpeakGrader>();
    return nullptr;
}
\end{lstlisting}

\subsection{Observer: \texttt{Subject/ProfileObserver} (Behavioral)}
\textbf{Location:} \texttt{code/core/domain/Subject.h}, \texttt{Profile.h}.\\
\textbf{Why:} Push XP/streak/skill/unit updates to UI without tight coupling.\\
\textbf{How:} Profile inherits Subject; ProfileView attaches; notifications on profile changes.\\
\textbf{Benefit:} UI stays in sync; supports future observers (analytics, badges).

\section{Features and Flows}
\begin{itemize}
  \item \textbf{Dual Streams:} Nepali and Kannada, each with structured units of 3 exercises.
  \item \textbf{Path Tab:} Shows unit status (completed/current/locked); admin override (admin123) to jump ahead.
  \item \textbf{Unit Completion:} Controller marks completion, persists profile, emits signal; UI shows confetti dialog with “Keep Learning.”
  \item \textbf{Exercises:} MCQ (click-to-fill), Translate (text or character selection with per-language sets), TileOrder, Listen (audio + MCQ), Speak (stub evaluator).
  \item \textbf{Audio:} Centralized via \texttt{AudioManager}; plays success/error and exercise audio paths.
  \item \textbf{Profile:} Tracks XP, streak, skills, and completed units per stream; date advancement button for streak testing (UI).
\end{itemize}

\subsection{Unit Progression Flow}
\begin{enumerate}[label=\textbf{\arabic*.}]
  \item User selects stream/unit (Home or Path). Controller loads stream and sets unit/exercise index.
  \item LessonView shows exercise; user submits answer; controller grades via Strategy.

class MockContentRepo : public IContentRepository {
public:
    MOCK_METHOD(std::vector<LearningStream>, loadStreams, (QString*), (override));
};

TEST(ControllerTest, StartsStreamWithMockRepo) {
    MockContentRepo repo;
    JsonProfileRepository profileRepo(":/tmp/profile.json");
    AppController controller(&repo, &profileRepo);
    std::vector<LearningStream> streams;
    LearningStream s("s1", "Stream 1", "L");
    Unit u("u1", "Unit 1");
    u.addExercise(std::make_unique<MCQExercise>("e1","p",{ "a","b" },0));
    s.addUnit(std::move(u));
    streams.push_back(std::move(s));

    EXPECT_CALL(repo, loadStreams(testing::_))
        .WillOnce(testing::Return(streams));

    controller.initialize();
    ASSERT_TRUE(controller.startStream("s1"));
    EXPECT_NE(controller.currentExercise(), nullptr);
}
\end{lstlisting}


\section{Error Handling}
\begin{itemize}
  \item Repo load/save errors surfaced via controller signal; UI shows message box.
  \item Missing audio: \texttt{AudioManager} no-ops if file absent.
  \item Path locking: enforces sequential units; admin override allowed via password.
  \item Controller guards: checks bounds on stream/unit/exercise indices and emits errors on invalid state.
  \item Content assumptions: minimal validation; future work includes stricter JSON schema and fallback defaults.
\end{itemize}

\newpage\section{Reflection}
The layered architecture and pattern choices ultimately made adding streams, units, and new exercise types straightforward, but arriving at this structure was iterative rather than obvious from the start. Early development surfaced a tension between breadth of features and end-to-end usability, which required repeatedly narrowing scope to stabilize a complete learning loop. Strategy kept grading isolated, Factory simplified content loading, and Observer kept the UI in sync; together, these decisions reduced rework as requirements evolved. As the system grew, the main risks became clearer. In particular, encountering ambiguous UI failures highlighted that functional correctness alone was insufficient without graceful failure modes. Extending gmock-based controller tests and adding persistence round-trips would further strengthen robustness. The dual-stream Listen/Speak structure reflects a deliberate balance between coherence and extensibility, leaving room for future language support without destabilizing the core system.

Lessons learned:
\begin{itemize}
  \item Prototype-to-architecture payoff: building a small end-to-end slice early clarified where real complexity lived and reduced controller churn when Listen/Speak requirements shifted.
  \item Data-driven content (JSON) reduced friction during iteration and enabled safer expansion, while forcing clearer decisions around per-language character sets.
  \item Testing built regression confidence, but integration gaps revealed the need to move coverage closer to controllers and mocks for stronger guarantees.
  \item UI resilience emerged as a trust issue rather than a cosmetic one; clearer error surfaces and loading states are essential to robustness.
  \item Documentation cadence matters: keeping diagrams and code aligned early reduced later decision friction and prevented unnecessary churn.
  \item Scope discipline required tradeoffs: stubbing Speak kept the project shippable and prevented audio handling from dominating development; future iterations should harden capture, permissions, and error handling once the core loop is stable.
\end{itemize}


\section{Future Work}
\begin{itemize}
  \item Replace Speak stub with real audio capture + ASR integration; richer Listen content.
  \item Expand tests with gmock for controller/repo interactions and malformed content coverage.
  \item Promote SQLite persistence to primary backend; add migrations and history tables.
  \item Improve Path/Unit UX (summaries, streak indicators) and enhance error feedback.
\end{itemize}

\section{Conclusion}
The final system delivers dual-language learning with structured units, clear progression via the Path tab, and integrated patterns (Factory, Singleton, Strategy, Observer) underpinning a layered architecture. Core logic is covered by GoogleTest; the design is extensible for additional languages, deeper audio, and stronger persistence while preserving clean separation of concerns.
